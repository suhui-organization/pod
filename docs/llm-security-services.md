# 大模型安全服务 — 架构与边界

> 状态：2026-09-12。本文回答"大模型在 pod 里能干什么、不能干什么、服务怎么卖"。
> 对应四条业界用法：SOC 大脑 / 精准内容识别 / 自动化红队 / 事件关联分析。
> 已落地部分见 §3（`pod redteam`）；未落地的决策见 §5。

---

## 0. 一句话

**大模型提建议，不判定，不执行。**

在 pod 里这不是一句口号，而是一条**机械强制**的路径：模型产出的是"数据"
（策略草稿、规则包、攻击场景），而任何会改变系统状态的入口都有一道它过不去的闸门
（签名 + 放宽守卫 + 纯函数判定器）。所以模型可以尽量大胆地想，因为它没有手。

---

## 1. 先解决一个矛盾

你列的四条用法里，"SOC 大脑"和"精准识别"默认都意味着**把安全数据送进模型**。
但 pod 最值钱的资产恰恰是 D3「本地优先」，而 T5「数据经 prompt 外泄给 LLM 提供商」
就写在自己的威胁模型里。这不是可以绕过去的小事：

> 一个"把审计日志发给云模型分析"的安全产品，自己在做它声称要防的那件事。

所以任何 LLM 能力在 pod 里都必须先回答一句：**什么数据出去了？**

### 沿用云端既有的三条约束

`cloud/server/app/services/llm.py` 已经定过三条，本地版本（`apps/cli/src/llm.ts`）照搬：

1. **出网一处**：所有模型调用走同一个函数，不各自发 HTTP；
2. **建议不决策**：模型输出永不改变策略/审批/告警状态；
3. **配置可解释、不静默回落**：选了 `mock` 就是 `mock`，绝不"以为在演示、其实在发请求"。

### 本地新增的第四条

4. **出网留痕**：每次调用（含失败）写一条 `kind='llm-call'` 进本地哈希链——
   只记 provider / model / 字符数 / 端点，**不记 prompt 正文**。

"数据不出机器"若是承诺，就必须能被查：什么时候、用什么模型、出去了多少。

## 2. 四条用法的落位

| 你的用法 | 在 pod 里的位置 | 出网面 | 状态 |
|----------|----------------|--------|------|
| **SOC 大脑**（调度、闭环） | 不做运行时大脑。做"建议物生成器"：策略草稿、规则包、处置剧本 | 只出权限面 | 刻意部分实现 |
| **精准内容识别**（提示注入等） | 网关分级注入词表（高置信默认阻断）+ G6 工具描述摘除 → 未来的分类器 | 必须本地 | 规则驱动部分已可用，模型分类待定 |
| **自动化红队** | `pod redteam`（本文 §3） | 只出权限面 | ✅ 已实现 |
| **事件关联分析** | `pod harden` 的 findings 解读 / 云端 `ai_summary` | 已掩码的 findings | 云端已有，本地待接 |

两条判断标准贯穿上表：

- **模型能不能碰到"判定"**——碰不到，"挡住没有"由纯函数说了算；
- **出网的是不是一个可审计枚举**——是，比如权限面就是 server/tool 名加三态位置。

### 出网前怎么裁剪（2026-09-13 收口）

云端告警摘要的出网口径定死在 `services/llm.py::shape_alert()`，四条：

1. **白名单字段**：只留 `ts / agent / severity / kind / message`（`OUTBOUND_KEYS`），
   工具参数、路径字段等一律不出网；
2. **路径打码**：`message` 里的文件路径换成 `<path>` —— 保留"在哪一层目录"这种对排查
   有用的结构，去掉用户名、项目名、文件名；URL 不误伤；
3. **命中密钥整条丢弃**：`message` 命中 `app.security.SECRET_PATTERNS` 就返回 `None`，
   那条告警整体不出网——不做"改一改再发"，密钥出现在这条链路本身就说明它不该被模型看见；
4. **如实报告剔除条数**：`ai_summary.build_context()` 会把"另有 N 条因命中密钥被剔除"
   写进上下文，免得模型以为拿到的是全量、得出"一切正常"的结论。

密钥规则**只有一份**（`app/security.py::SECRET_PATTERNS`），策略模板的
`deny_output_matching`（拦工具输出）与这里（拦出网）共用——两处各写一份，
拦住的那批和发出去的那批迟早会变成两个集合。写这条时对齐现实还发现过一次漏网：
`sk-[A-Za-z0-9]{20,}` 拦不住现在的 `sk-proj-…`（连字符挡住），已改成 `sk-(?:proj-)?`。

> 已知遗留：本地 CLI 还有**另一份**同义的规则（`packages/scan/src/index.ts`，TS），
> 跨语言没法共用，两边只能靠人对照。已知它比服务端多 `PRIVATE KEY` 头，
> 服务端刚补齐了它多出来的 `gho_` / `glpat-`；下次动任何一边，记得看另一边。

### 为什么"不做运行时大脑"是刻意的

让模型进每一次工具调用的判定路径，会同时破坏三件事：本地优先（每次调用都要出网）、
延迟（网关热路径变成秒级）、可复现性（同一个调用今天放行明天拒绝，无法向审计解释）。
这正是 D2「策略与审批为主，异常检测为辅」的延长线——
**可判定规则 > 模型判定 > 统计信号**；模型的位置在第二档，且必须被第一档兜住。

如果将来要做，前置条件是"本地模型 + 明确 opt-in + 判不了时回落到确定性规则"，
见 §5 的决策点。

## 3. 已实现：`pod redteam`

```bash
# 1) 纯离线：内置场景库，不需要任何模型
pod redteam --policy ~/.pod/policies/draft.json

# 2) 带模型：模型只负责"想出攻击"，判定仍由 pod 做
pod redteam --policy <p> --llm --provider deepseek

# 3) 离线交接（客户不想让任何东西出网时）
pod redteam --policy <p> --export-surface surface.json     # 导出权限面
#    ……把 surface.json 交给任意模型/人工，拿回 scenarios.json……
pod redteam --policy <p> --scenarios scenarios.json        # 校验 + 确定性执行
```

### 3.1 分工

```
      模型（可选）                      pod（不可插拔）
  ┌──────────────────┐          ┌───────────────────────────┐
  │ 读权限面          │          │ 校验场景（含"不许编造"）    │
  │ 产出攻击场景 JSON  │ ───────▶ │ decideCall() 纯函数判定    │
  └──────────────────┘          │ 报告：挡住 / 绕过           │
                                └───────────────────────────┘
```

### 3.2 为什么这样是安全的

- **模型产出的是数据，不是代码**：场景被解析成 JSON 后只喂给判定器；
- **判定是纯函数**：`decideCall`（网关里那个"策略求值 + egress 合并"）不产生任何副作用；
- **不真的调用 MCP server**：场景只在策略层"被判"，所以它碰不到客户数据；
- **校验器挡住"自我拔高"**：模型若编造 server/tool，那些调用一律被 fail-closed 拒绝，
  于是"挡住 N 个"会被刷得很漂亮却毫无信息量。校验器直接丢弃这类场景并说明原因。

### 3.3 判定流水线必须与网关同源

红队报告里"挡住"三个字必须和真实网关的结论一致。因此这次把
`evaluate()` + `checkEgress()` 的合并逻辑抽成了 `decideCall()`，网关注册表和红队共用它。
两边各拼一遍判定，迟早漂移——而漂移的后果是"报告说挡住了，网关其实放行"，
那比没有红队更糟。

不在流水线里的一层是**熔断**：`quarantine` 是运行时状态而非策略判定，
被熔断的 agent 一律 deny，与策略无关，所以不进这个纯函数。

### 3.4 能挂 CI

有高危绕过时退出码 1（与 `pod posture --strict`、`pod graph toxic` 同惯例）。
`scenarios.json` 把生效场景固化下来，于是"策略改动 → 红队复跑"成为一条回归测试，
不需要再过一遍模型。

### 3.5 明确没做的

- **没有对运行中的系统发起真实攻击**：v1 只做策略层判定。真正的"攻击"要驱动网关
  发 MCP 调用，那是下一步（`--live`），代价是它会真的碰数据，必须单独设计；
- **不理解编码后的载荷**：`secrets.deny_input_paths` 是路径段匹配，base64 过的敏感路径
  不会命中。这条边界写进了报告，不假装覆盖；
- **不是渗透测试**：不进 v1 服务清单。

## 4. 为什么"LLM 提议 + 机械闸门"是 pod 的独特位置

同类产品让模型"别乱来"靠的是提示词（约定）；pod 有一条**机制**：

| 环节 | 一般做法 | pod 的做法 |
|------|----------|------------|
| 模型提策略 | 直接落库/生效，靠提示词约束 | 落成**草稿**，人工复核后才启用 |
| 模型提规则 | 直接写入规则文件 | 落成**签名规则包**，且过**放宽守卫**（削弱已有规则直接拒绝） |
| 模型提攻击场景 | 直接执行 | 只作为**数据**喂给纯函数判定器 |
| 模型调用本身 | 不记录 | **写进哈希链**（`llm-call`），含失败尝试 |

正因为生效路径上有一道它过不去的闸门，模型的能力才可以被放到最大——
这是"用大模型做安全"最反直觉也最有用的一条：**先给它上闸门，再让它放开想。**

## 5. 还没做、需要你拍板的

### 决策 1：运行时模型判定要不要做

在网关热路径上用模型判"这次调用危不危险"。收益是能抓规则写不出来的语义风险；
代价是延迟、不可复现、以及必须出网（或必须本地部署一个小模型）。
现状：**没做**，理由是 §2 那三条。

### 决策 2：提示注入的模型分类器放哪

网关现在用 `rules.injection.signals` 做分级子串匹配（用户可编辑、离线、可解释，
但只能抓已知措辞）：高置信信号默认阻断该次工具响应，中低置信只标记
（分级理由见 `docs/attack-verification.md` §3.1）。

模型分类器能抓没见过的措辞，但：

- **本地小模型**：不出网、无延迟代价可接受，但要引入模型分发与体积问题；
- **远程 API**：效果最好，但等于把**工具响应正文**发给模型——那是 T5 本身。

这是本批最需要你判断的一条，因为它直接决定产品要不要背一个模型运行时。

### 决策 3：服务形态里谁跑模型

- 客户自己配 key（`~/.pod/llm.json`）——数据从客户机器直连模型厂商，我们不碰；
- 我们代跑（客户只把权限面/掩码 findings 交给我们）——我们能控制提示词质量，
  但变成了数据处理方，要写进隐私声明与合同。

### 已知偏差（顺手发现，未修）

`docs/egress-defense.md` 与 `rules.ts` 的示例里出现过通配写法 `*.telemetry.example.com`，
但 `hostMatches()` 的实际语义是：以 `.` 开头才是后缀匹配（`.telemetry.example.com`），
其他一律精确匹配。**写成 `*.x.com` 会静默不生效**。红队生成器已按真实语义构造 URL，
但文档示例建议改掉，或给 `hostMatches` 补通配支持。

## 6. 服务化：四种可卖形态

| 形态 | 卖什么 | 模型在哪 | 数据出网 |
|------|--------|----------|----------|
| **红队体检（一次性）** | "你的策略挡住了 N 个攻击场景，这 3 个没挡住" | 我们侧生成场景 | 只有权限面 |
| **规则订阅（已有）** | 对抗知识持续更新 | 我们侧用来**写**规则包，客户侧不跑模型 | 无（客户端离线） |
| **审计报告解读（LLM 增强的 A）** | 在 `pod harden` 报告上加一层叙述与优先级建议 | 客户配 key，或我们代跑 | 已掩码 findings |
| **托管分析** | 跨机器聚合 + 告警分诊 | 我们侧 | 只收 findings/摘要，不收审计原文 |

前两种不依赖客户跑任何模型，也不依赖我们持有客户数据——这是与"本地优先"最相容的
两条线，建议先走这两个。
